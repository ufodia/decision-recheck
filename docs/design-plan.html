Final decision / build an application pack

Create a small open-source SaaS audit pack with a local CLI and skill entry point. Use existing browser and evidence-freshness infrastructure. Add scoped offer/task checks, reviewable evidence and three useful report views: product owner, buyer, and marketing/support.

The product is the repeatable review workflow and its test cases. A new general-purpose agent framework or freshness engine is unnecessary.

03 / Frozen v0.1 scope

Inputs and limits

  • One authorized web application; one explicitly selected plan, locale, currency and billing basis per case.
  • Three to five user requirements, up to ten supplied or reviewed claims, and at most eight approved source URLs in total.
  • Optional public-document comparison for one alternative. Its browser behavior remains untested.
  • Up to three task attempts per snapshot, each in a separate context: understand a plan; perform one core/export task; find the relevant help or exit information. One comparison includes a baseline and one explicit recheck, at most six attempts across the pair.
  • Supplied advertisement/offer text and selected pricing/product/help content. No campaign-account connection is needed.

Required deliverables

  • Local CLI, a portable skill entry point and a model-free fictional fixture.
  • Versioned JSON evidence bundle with captured artifacts and referenced freshness receipts.
  • Three English report views and a reviewed old-versus-new decision summary.
  • Scoped recheck against current sources and relevant task outcomes.
  • A complete partial report when work is blocked, canceled, missing or over budget.

Deferred: broad web crawling, many-product procurement suites, demographic persona panels, scheduled cloud monitoring, ad-platform integrations, production purchases, account creation, subscription cancellation, outbound support messages and automatic issue publication. Exit-route inspection stops before cancellation or another destructive action.

Production inspection is limited to approved public/read-only tasks. Task execution that creates or changes data uses a designated test environment with synthetic data and an explicit action allowance. The runner does not attach to the operator's personal browser profile.

04 / Complete review workflow

01 / BRIEFRequirements, claims, scope and permissions
02 / CAPTURESources and isolated task evidence
03 / REVIEWSupport, conflict, fit and unknowns
04 / REPORTOwner, buyer and marketing/support views
05 / RECHECKCurrent sources, affected tasks and decision changes
  1. The operator reviews the generated brief, scope and planned actions. Inferred requirements are labeled and require acceptance before they become hard constraints.
  2. The collector captures selected source fields/excerpts with time and scope. Actor sessions receive a goal and allowed actions, without seeing another actor's conclusions.
  3. The offer/support analyst links claims to relevant artifacts. A deterministic validator rejects broken source IDs, missing scope and invalid record shapes.
  4. The evidence reviewer checks material findings and contrary evidence. Unreviewed AI conclusions stay proposed.
  5. The local report shows coverage, accepted findings, disagreements and missing work. It may propose a decision; a human accepts or rejects it.
  6. A later recheck refetches the scoped live source, preserves the old observation and uses the configured freshness layer to identify affected dependencies. Relevant tasks are rerun within the approved allowance.
  7. The decision summary explains which conclusions changed, which remained supported, and which are now unknown. A wording repair does not automatically repair product fit.

Immediately before writing a report labeled current, place the actual report-writing callback behind the verified FreshCtx revalidation boundary. Stale or unverifiable dependencies prevent that current-status export. A clearly labeled historical or partial report remains available through a separate path. Display the check time and checked fields; no report promises indefinite currency. Task results retain their attempt time and require a new attempt before being described as freshly tested.

Fictional release demonstration

A: Starter costs $9/month, CSV export works, and the buyer's maximum budget is $20/month. The offer and help text agree.

B: Starter becomes $29 and export moves to $49 Pro. The old ad and help answer remain. Recheck shows a plan/task discrepancy, a buyer budget failure and stale wording.

C: Ad/help wording is corrected. The documentation issue resolves; the buyer's budget failure remains.

Control: only the footer changes. Relevant scoped observations stay equivalent; no full task rerun should be required. The repaired C snapshot is a separate explicit recheck with its own allowance, not an unbudgeted third snapshot.

Critical distinction: checking the hash of an archived screenshot only establishes that the archive did not change. A current-source check must actually revisit the scoped live source. A successful check does not establish truth, human usability or future availability.

06 / Evidence and decision contracts

Requirement → Scoped claim → Source / Task check → Finding → Decision

Stable IDs connect records to the upstream freshness receipts. Every material item includes product/plan/locale scope, capture time, source kind, method, producer, reviewed status and contrary evidence. Task records add starting state, permitted actions, actual action events, expected/observed outcome and artifact locators. Store concise reasons and observable events, not private model reasoning.

Separate axisExamplesRule
ExecutionNot run · completed · failed · blocked · interruptedA blocked task does not prove a feature is absent.
Evidence basisVendor claim · vendor document · observed task · supplied user evidenceSeveral agents citing one source remain one source.
Claim supportSupported within scope · conflicting · insufficientDocuments and observed behavior remain distinguishable.
FreshnessCurrent within checked scope · changed · unverifiable · historical onlyRetain upstream state details. Current is not synonymous with true.
Requirement fitMeets · fails · conditional · inconclusiveA hard-constraint failure cannot be averaged away by unrelated strengths.
ReviewProposed · accepted · rejected · review requiredNew evidence may reopen review without erasing the old decision.

Price comparisons must share currency, billing period, tax basis and required plan. Annualized or ambiguous offers remain conditional until normalized. Source canonicalization may ignore a cosmetic region only when the chosen field scope and rule are recorded. A missing selector, empty extraction, changed extractor version or ambiguous parse requires review and cannot silently become current. Ambiguous semantic changes create review tasks rather than automatic truth judgments.

07 / Agent contracts and operating limits

RoleInput → outputBoundary
Requirements researcherOperator brief and approved sources → explicit criteria and source candidates.No silent hard-constraint inference; no unbounded crawling.
Task actorsOne goal, declared constraints and clean test session → actual steps, outcome and artifacts.Up to three attempts per snapshot; no peer conclusions; approved tools only.
Offer/support analystClaims, docs and task evidence → supported/conflicting/insufficient proposals.Cannot treat a sales answer as independent proof.
Evidence reviewerProposed findings and artifacts → checked references, objections and accepted/rejected proposals.Agreement is not evidence; preserve unresolved disagreement.
Report writerValidated records and reviewed decisions → three audience views.No new facts, invented source IDs or fabricated commercial forecasts.

The coordinator is ordinary deterministic code. Per-snapshot default: at most two concurrent browser sessions, twelve permitted browser actions per task, thirty-six browser actions total, forty model calls and a twenty-minute deadline. A baseline/recheck pair has an explicit aggregate allowance of at most seventy-two browser actions, eighty model calls and forty minutes; the configured case budget can reduce these limits. Caps include research, actors, synthesis, review, report writing and retries. These are initial caps, not measured performance promises. Live mode also requires a configured token cap and operator spending ceiling when enforceable; the adapter reserves a conservative per-call allowance before dispatch.

Provider prices and actual usage must be timestamped and labeled. A hard monetary ceiling is claimed only when the adapter can enforce a conservative bound; otherwise expose call/token/time caps and mark monetary usage unavailable or estimated. No paid inference is needed for the fixture demo. No automatic provider fallback or added calls occur after a cap is reached.

Five roles do not imply five independent models or human respondents. Compare the role-separated pipeline with a single-agent baseline at the same resource limits; keep additional sessions only when they improve verified outcomes.

08 / Execution, privacy and partial failures

  • Enforce domain and action allowlists before tool execution, including redirects and new navigation targets. Restrict arbitrary script execution and external data egress.
  • Default to public read-only pages. Permit synthetic test writes only for the specific test application and actions declared in the brief.
  • Treat page text, downloaded material and imported reports as untrusted data. They cannot change tools, permissions, budgets or report instructions.
  • CAPTCHA, authentication, expired sessions, rate limits and unavailable sources become explicit blocked/unverifiable results. No bypass or invented success.
  • Use disposable synthetic inputs. Credentials stay outside bundles; raw traces can contain sensitive data and remain local unless a reviewed redacted export is deliberately shared.
  • Local execution does not mean a configured cloud-model adapter receives no data. Describe the exact page excerpts/artifacts sent and keep telemetry off by default.
  • Escape all source text in HTML reports. Export manifests list included and omitted artifacts; missing, corrupt or altered files cannot appear as verified evidence.
  • Cancel and resume at stage checkpoints with idempotent local records. An uncertain interrupted write is recorded for human reconciliation, never blindly replayed.

Deployment of a future documentation/demo site is a separate delivery step. Vercel would host static documentation and a clearly labeled recorded/fixture demonstration; browser execution and long agent runs stay local. Live site publication and any associated Search Console changes follow the user's applicable authorization rules.

12 / Launch, contribution and support plan

English launch message: “Your product changed. Which buying advice, campaign claim and support answer should change with it? Decision Recheck connects scoped source checks and real test tasks to three reviewable reports.”

  1. Before launch: publish the model-free A/B/C demo, full fixture results, upstream credits and a short limitations page. Ask pilot participants for consent before naming them or sharing their material.
  2. GitHub launch: use one annotated before/after example, a 60–90 second recording, three report images and small contribution issues: a source extractor, a clean control, a false-positive reproduction or a task fixture.
  3. LinkedIn launch package: prepare three original English visuals: changed offer, reproduced task result, three affected decisions. Each visual shows concrete evidence and clear typography. Publish only measured results and label the fictional example.
  4. Buy Me a Coffee: add an optional support ufodia button in the README and demo. Explain that support funds fixture maintenance, compatibility checks and documentation. Keep core functionality and the offline demo free.
  5. First month: share one reproducible case or fix weekly, publish a short changelog and invite narrowly scoped contributions. No artificial testimonials or unsupported “world first” headline.

Measure GitHub visitors/stars where available, completed demos, valid issue reports, LinkedIn engagement and actual support events separately. Use tagged launch links and optional project identifiers for attribution; shared Buy Me a Coffee payments without reliable attribution remain unattributed. No donation or revenue target is presented as a forecast.

13 / Research record and remaining uncertainty

The implementation decision is final for this plan: an adapter-first SaaS audit pack, not a new generic reasoning or freshness platform. Remaining engineering uncertainty belongs in the compatibility spike; remaining demand uncertainty belongs in the pilot.

  • FreshCtx repository, official overview and adapter contract: existing dependency/freshness mechanisms and integration boundaries.
  • Lodestar and Sevenbox: adjacent decision-tracing systems and licensing distinctions.
  • MarketMirror, Buyer Eval and Chaosfolk: existing marketing, buyer and browser-audit workflows.
  • Playwright isolation, trace documentation and Agent Skills specification: intended infrastructure and packaging.
  • When Synthetic Users Fail (preprint): reports limits under its demographic-prompting survey protocols across two domains. It is not a direct validation of this browser-task pack; its abstract supports caution about treating synthetic respondents as real people.
